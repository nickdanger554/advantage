# StoreAdOps Claude package 0.6.1

## Package contract

- Production endpoint: `https://app.storeadops.ai/mcp/packs/ads-v3`.
- Four skills: get started, performance review, daily profit brief and campaign draft.
- The skill bodies and references come from the shared generated Claude skill
  distribution; only the host overlay differs from the OpenAI distribution.
- Public tool names and operations are different concepts. Discover the exact
  operation contract and use the `request` envelope; legacy names are not aliases.
- Reads stay bounded. Report-job creation is an explicit provider effect, not a
  pure read. Partial data and unavailable data are not reported as complete or zero.
- Change previews and confirmation happen in chat. A browser is used for OAuth
  and account selection, not a mandatory change-approval step. Preparation does
  not execute a provider write. Uncertain execution retains the original plan
  and idempotency key for reconciliation.
- Account, permission and feature gates remain server-authoritative. Shopify
  access is read-only. This package changes no OAuth settings or provider state.
- The V1 growth-action-graphs files are retained under `legacy/`, outside the
  installed plugin, rather than exposed as an unsupported ads-v3 workflow.

## Validation boundary

The shared source passes schema and secret-pattern validation, 42 deterministic
guidance scenarios, generated-output parity, and 52 unit tests. These are local
checks, not proof that a model selected and followed a skill in a conversation.
The public package also passes strict Claude marketplace and plugin validation,
frontmatter validation for all four skills, a scoped secret-pattern scan, and
byte-for-byte parity for all nine generated skill files. The canonical bodies
and references match the submitted OpenAI package; the host overlays differ.
Offline checks against the server schemas validate two documented calls and
three negative cases without provider I/O.

An isolated fresh GitHub installation loads 0.6.1 with four skills and one MCP
server. The isolated 0.6.0 installation also upgrades to 0.6.1, and its existing
production ads-v3 OAuth connection remains connected. Fresh OAuth was verified
for the earlier 0.6.0 candidate; the upgrade check reuses that grant rather than
claiming a new grant. These observations do not establish conversation-level E2E
for 0.6.1, which remains unverified. No paid model access, provider writes or
report jobs were used by these package checks. Directory acceptance is separate
from GitHub distribution.

## Updates and rollback

Both the marketplace and plugin manifests declare 0.6.1 so an existing 0.5.1
or 0.6.0 installation can recognize the update. Use the update commands in the
repository README, reload the plugin, and check `/mcp`. An upgrade from the old
MCP URL may require OAuth again; never copy tokens into plugin configuration.

The previous public baseline is tag `v0.5.1`, commit
`3ecd025619b842d0fd002795fcc58d78f5cf1187`. Roll back through a reviewed revert and
a new higher package version so clients actually receive it; do not overwrite
history or assume reducing the version will update installed clients.
